# Техническое задание: ChatNovella Lite

## 1. Цель проекта

Создать упрощённый, работоспособный серверный движок интерактивных новелл на основе существующего репозитория **`ioshi9212-dotcom/ChatNovella`**.

**Главный принцип:**

- ChatGPT пишет художественные сцены, управляет NPC и развитием сюжета.
- Сервер надёжно хранит анкету, отношения, личные знания, хронологию, текущее состояние и полную историю.
- Каждый ход ChatGPT получает полный утверждённый канон и необходимые игровые данные.
- Информация не теряется, не сокращается молча и не переносится между персонажами без основания.

**Приоритет — простая, работающая система. Не усложнять архитектуру без технической необходимости.**

Это новая тестовая версия, а не модернизация всей старой инфраструктуры.

## 2. Репозитории и безопасность разработки

**Основной репозиторий:**

`ioshi9212-dotcom/ChatNovella`

Создать отдельную рабочую ветку, например:

`feature/chatnovella-lite`

**Запрещено без отдельного разрешения:**

- изменять `main`;
- автоматически сливать рабочую ветку;
- развёртывать новую версию на действующий сервер;
- менять существующие игровые сессии и их данные;
- удалять старые файлы или историю;
- переносить решения из старых репозиториев целиком без оценки необходимости.

Для изучения и точечного заимствования механик использовать:

| Репозиторий | Нужная механика |
|---|---|
| `ChatNovella` | Хранение, контекст, история, состояние, хронология, аудиты |

| `new_1206_v3` | Выбор NPC для загрузки контекста |

| `ai_novella` | Дополнительные тесты памяти и непрерывности |

Не переносить старую многослойную архитектуру RomanAI.

## 3. Структура файлов

Реализовать минимальную структуру:

```text
engine/
    rules.md
    skin_builder.md

sessions/
    <session_id>/
        original.md
        novel.md
        relationships.md
        state.md
        timeline.md
        history.jsonl

        knowledge/
            NPC_001.md
            NPC_002.md
            ...

        system/
            meta.json
```

### Назначение файлов

**`original.md`**

Дословный исходный материал читателя. Неизменяемый архив. Не загружается на каждом игровом ходе.

**`novel.md`**

Полная окончательная анкета после согласования с читателем. Включает все утверждённые сведения, биографии, мир, лор, правила, предысторию и сюжетные условия без сокращений.

В конце — технический реестр постоянных ID персонажей.

Загружается **полностью каждый игровой ход**.

После утверждения не изменяется игровым процессом.

**`relationships.md`**

Единый файл всех актуальных отношений и правил их изменения.

Создаётся при настройке новеллы и загружается полностью каждый ход.

**`state.md`**

Актуальное физическое и временное состояние сцены. Обновляется каждый ход.

**`timeline.md`**

Объективная хронология событий, произошедших в игре.

**`history.jsonl`**

Единый журнал всех полных игровых ходов. Никакого распределения истории по десяткам файлов.

**`knowledge/NPC_ID.md`**

Отдельная приобретённая память конкретного NPC.

**`meta.json`**

Технические данные: версия, ID, количество ходов, хеш анкеты, состояние аудита и сведения для восстановления.

Не создавать дополнительные runtime-файлы, если их функцию выполняют существующие.

## 4. Создание новой новеллы

Последовательность:

1. Читатель присылает анкету текстом, частями или файлом.
2. GPT читает весь материал.
3. При необходимости задаёт вопросы о противоречиях и недостающих важных данных.
4. GPT готовит полную согласованную версию, сохраняя авторские факты и формулировки.
5. Всем персонажам присваиваются постоянные ID: `POV_001`, `NPC_001`, `NPC_002` и далее.
6. Из анкеты формируется **один начальный файл отношений**.
7. Создаётся начальный `state.md`.
8. Читатель явно утверждает окончательную анкету.
9. Сервер фиксирует её и контрольную сумму.
10. Первая сцена запускается только по отдельной команде читателя.

### Важнейшие ограничения

Не создавать при настройке:

- отдельные файлы биографий каждого NPC;
- отдельные файлы внешности, характера, голоса и прошлого;
- пересказы всей анкеты;
- дублирующую структурированную версию каждого раздела;
- заполненные сведениями анкеты личные журналы знаний NPC (пустые файлы
  по зарегистрированным ID создаются сразу и не являются карточками);
- заполненную хронологию из всей предыстории.

**Предыстория находится в анкете. Хронология фиксирует то, что происходит в игре.**

В `novel.md` сохранить полный утверждённый материал, а не краткую выжимку.

Проверить дословность исходного материала и согласованных изменений.

После утверждения `novel.md` заблокирован от автоматического изменения. Авторские поправки возможны только после явного разрешения читателя и создания новой проверяемой версии канона.

## 5. Механика отношений

Создать один `relationships.md`.

### NPC → POV

Числовые направленные отношения.

Правила:

- Допустимые значения: 0–100.
- Набор показателей индивидуален для каждого NPC.
- Не использовать обязательные одинаковые шкалы для всех.
- Начальные значения формируются по утверждённому канону; если числа не даны автором, это игровые оценки GPT, которые читатель может исправить до утверждения.
- Обычное изменение существующего показателя: не более ±3 за ход.
- При действительно значимом событии разрешены большие изменения.
- Отсутствие причины означает отсутствие изменения.
- Менять только затронутые показатели.
- Новая эмоциональная шкала может возникнуть при обоснованном развитии отношений.
- Достигший нуля показатель может удаляться.
- Не записывать в отношения кратковременное настроение вместо устойчивого чувства.
- Не заставлять чувства расти или ухудшаться каждый ход.

### NPC → NPC

Только качественные, направленные отношения **словами, без чисел**.

Например:

```text
NPC_001 → NPC_002:
Считает братом, но не доверяет его решениям.

NPC_002 → NPC_001:
Любит брата, скрывает от него важную информацию.
```

Направления могут различаться.

Отношения могут изменяться в результате событий игры, включая обоснованные события за кадром.

**Нельзя придумывать изменение отношений только ради динамики.**

Файл хранит актуальное состояние. Подробные изменения и их причины остаются в журнале игровых ходов.

## 6. Личная память NPC

### На старте

Знания до начала игры содержатся в полной анкете.

Не дублировать их автоматически в отдельные файлы.

### Во время игры

Создавать пустой `knowledge/NPC_ID.md` при регистрации постоянного NPC.
При первом новом приобретённом знании дополнять только его собственный файл.
Запись хода требует `knowledge_review` по каждому участвовавшему NPC
(recorded/none); несоответствие этому отчёту сервер отклоняет.

Каждая запись должна содержать:

- номер хода;
- игровую дату, если она известна;
- конкретный факт или предположение;
- источник получения информации;
- статус: знает / предполагает / ошибочно считает / выяснил, что это неправда.

Пример:

```text
Ход: 17
NPC: NPC_001

Факт:
Акира встречалась с Джуном.

Источник:
Рэй лично видел их вместе.

Статус:
Знает достоверно.
```

### Правила знания

- NPC знает только то, что установлено его исходным каноном или получено им допустимым способом.
- Общая анкета не означает, что каждый NPC знает все её сведения.
- Хронология мира не равна личной памяти NPC.
- Мысли POV в скобках не являются произнесёнными словами.
- Личная переписка доступна её участникам, а не всем присутствующим.
- Можно ошибаться, подозревать, скрывать сведения или лгать.
- Отсутствующий NPC не узнаёт автоматически о событиях сцены.
- Новое знание записывается только при наличии источника.
- Старые записи не удаляются бесследно при уточнении или опровержении.

### Загрузка

При подготовке сцены определять NPC по постоянным ID.

Загружать личные знания физически присутствующих и удалённо участвующих NPC, если они действительно участвуют во взаимодействии.

Если новый NPC вступает в сцену, его необходимые знания должны быть загружены **до окончательного написания соответствующего эпизода**.

Не читать персональную память всего состава персонажей на обычном ходу.

## 7. Хронология

Использовать надёжную механику хронологии из ChatNovella, адаптированную к одному `timeline.md`.

Начальная хронология пуста.

При значимых игровых событиях добавлять записи:

```text
Ход: 24
Дата: 12.09.2026
Участники: POV_001, NPC_001, NPC_002

Событие:
Рэй увидел встречу Акиры и Джуна.

Последствие:
Рэй узнал о встрече.
Отношение Рэя к Акире изменилось.
```

### Правила

- Хранить события по игровым датам и номерам ходов.
- Не придумывать отсутствующие даты.
- Не пропускать значимые события.
- Не создавать записи из бессмысленных бытовых мелочей.
- Не переписывать прошлое задним числом.
- Сохранять важные последствия и незавершённые сюжетные линии.
- Не превращать хронологию автоматически в личное знание персонажей.
- Для новой вехи передавать `significance` из допустимых типов
  turning_point/revelation/irreversible_change/commitment/major_consequence
  и конкретную `significance_reason`. Длина event ≤350 символов, consequence
  ≤220 символов. Не дописывать дубликаты того же события.
- Личная новость за кадром без глобального последствия пишется прямо в
  knowledge с конкретным source/evidence, без выдуманного события хронологии.
- Оригинальные сцены всегда остаются в `history.jsonl`.

Важное событие может одновременно обновить хронологию, память конкретного NPC и отношения. Это три разные записи с разным назначением.

## 8. Текущее состояние сцены

Использовать один `state.md`.

Обязательные сведения:

- текущий номер хода;
- дата и время мира;
- локация;
- POV: положение, одежда, обувь, предметы, физическое состояние, незавершённые действия;
- присутствующие NPC по ID;
- их положение, одежда, предметы и текущие действия;
- удалённые участники связи;
- существенные объекты окружения;
- незавершённые взаимодействия.

Файл обновляется **каждый ход**. Новая запись знаний («NPC узнал/не знает/
слышал/видел») в `state_patch` запрещена: это личная память, не состояние
места или тела. Старые данные требуют отдельной сверки, не автоочистки.

Неизменившиеся детали должны сохраняться.

Не телепортировать персонажей и предметы. Не менять одежду, расположение или время без причины.

## 9. Полная история

Сохранять всё в **одном `history.jsonl`**.

Каждый завершённый ход содержит:

- номер хода;
- дословный ввод читателя;
- полный окончательный текст сцены;
- изменения состояния;
- изменения отношений;
- приобретённые знания;
- события хронологии;
- техническую версию сохранения.

Не заменять художественные сцены краткими сводками.

При обычной подготовке следующего хода загружать последние 2–3 полные сцены.

Старый архив доступен для аудита, поиска, проверки непрерывности и восстановления.

Реализовать безопасный откат последнего хода с восстановлением всех затронутых данных.

## 10. Подготовка каждого игрового хода

Один игровой цикл:

**Шаг 1.** Получить дословный ввод читателя.

**Шаг 2.** Загрузить полностью:

```text
engine/rules.md
engine/skin_builder.md
sessions/<id>/novel.md
sessions/<id>/relationships.md
sessions/<id>/state.md
sessions/<id>/timeline.md
```

Также загрузить последние 2–3 полные сцены.

**Шаг 3.** Определить персонажей, участвующих в текущем эпизоде.

**Шаг 4.** Загрузить их личные файлы знаний при наличии.

**Шаг 5.** GPT пишет художественную сцену с соблюдением всех художественных правил Skin Builder и технических ограничений.

**Шаг 6.** Определить фактические изменения состояния, отношений, знаний и хронологии.

**Шаг 7.** Одним атомарным сохранением записать сцену и необходимые изменения.

**Шаг 8.** Только после подтверждения успешной записи показать читателю сохранённую сцену.

### Обязательные технические гарантии

- Полный `novel.md` передаётся без усечения.
- Если файл не помещается в один ответ, используются чанки.
- Все чанки должны быть прочитаны и проверены по контрольной сумме.
- При неполном контексте не продолжать написание сцены как будто всё загружено.
- При повторе одинакового запроса не создавать дублирующий ход.
- Не сохранять изменения поверх устаревшей версии состояния.
- Не показывать сцену как успешно сохранённую, если запись не завершилась.
- При ошибке сохранять предыдущую целостную версию данных.
- Не смешивать данные разных игровых сессий.

Не вводить обязательное составление режиссёрского плана через отдельный серверный вызов.

## 11. Rules и Skin Builder

Каждый ход обязательно загружать оба файла.

**`rules.md`** — только техническая работа системы: создание, загрузка, ID, контекст, память, отношения, хронология, сохранение, аудиты и ошибки.

**`skin_builder.md`** — художественные правила: POV, NPC, стиль, диалоги, формат, режиссура, автономия персонажей и развитие сюжета.

Сохранить утверждённые пользовательские правила художественного поведения без самовольного смягчения и изменения.

Не вводить третий обязательный файл `scene_review.md`.

Не переносить старую систему обязательной оценки каждой сцены по 11/12 баллам.

Оставить необходимые технические проверки корректности файлов и сохранения.

## 12. Аудиты

Реализовать обязательные контрольные точки.

### Каждые 15 ходов

После ходов 15, 30, 45, 60 и далее:

- прочитать полные сцены последнего блока из 15 ходов;
- проверить непрерывность событий;
- проверить отношения и обоснованность изменений;
- проверить личные знания участвовавших NPC;
- проверить даты, время, перемещения и фактическое состояние;
- проверить отсутствие пропущенных важных событий в хронологии;
- исправить подтверждённые расхождения без переписывания авторского канона.

Не начинать следующий ход до завершения обязательного аудита.

### Каждые 60 ходов

В дополнение к очередному 15-ходовому аудиту:

- проверить полную накопленную хронологию;
- проверить личные знания **всех NPC**, включая отсутствующих;
- проверить долгосрочные сюжетные последствия;
- проверить непрерывность отношений;
- обнаружить забытые или противоречивые события.

Исходный архив сцен не сокращать и не удалять.

Компактизация допускается только для производных данных и только при сохранении исходных фактов и источников.

Не создавать отдельные файлы аудита в пользовательской структуре. Технические результаты хранить во внутренних метаданных или архиве операций.

## 13. Этапы разработки

### Этап A — базовая архитектура

Реализовать минимальные шаблоны файлов, изоляцию сессий, загрузку полного канона и реестр ID.

**Приёмка:** новая сессия создаётся, утверждённая анкета блокируется, её исходник сохранён дословно, все 50 000+ символов приходят в контекст без потери.

### Этап B — отношения

Подключить единый `relationships.md`.

**Приёмка:** сохраняются начальные отношения, числовые NPC→POV и словесные NPC→NPC. Изменяются только нужные записи. Нулевая дельта допустима.

### Этап C — личные знания

Реализовать персональные файлы NPC и выборочную загрузку по ID.

**Приёмка:** персонажи помнят приобретённые сведения, но не получают чужие знания или закрытую информацию автоматически.

### Этап D — хронология и состояние

Подключить `state.md` и `timeline.md`.

**Приёмка:** положение персонажей, время, предметы, сюжетные события и последствия сохраняются между ходами.

### Этап E — сохранение и восстановление

Реализовать запись всех изменений за одну операцию, полный журнал истории, безопасные повторные запросы и откат.

### Этап G — тестирование

## 14. Обязательные тесты

Проверить как минимум следующие случаи:

1. Анкета объёмом более 50 000 символов, кириллица, много NPC, несколько чанков.
2. Изменение канона невозможно без утверждения читателя.
3. Все ID стабильны после перезапуска.
4. Два NPC имеют противоположные отношения друг к другу.
5. Числовые отношения меняются на ±1–3, при отсутствии причин остаются неизменными.
6. NPC отсутствует и не получает знания из чужой сцены.
7. NPC участвует в телефонном разговоре и получает именно услышанные сведения.
8. NPC ошибочно предполагает факт, затем выясняет правду.
9. Персонаж входит в сцену — его личная память загружается до написания взаимодействия.
10. Существенное событие корректно попадает в хронологию.
11. Незначительное действие не создаёт ненужных записей.
12. Состояние одежды, предметов и положения сохраняется.
13. Сбой при сохранении не создаёт частично обновлённое состояние.
14. Повтор одного запроса не дублирует игровой ход.
15. Откат возвращает состояние, отношения, знания и хронологию.
16. Аудит после 15-го хода действительно сверяет полные сцены.
17. Аудит на 60-м проверяет знания всех NPC.
18. Возобновление истории после перезапуска сервера.
19. Две независимые новеллы не смешивают данные.
20. Проверка реальных художественных сцен, а не только синтетических тестов.

**Минимальный полноценный прогон — 60 последовательных игровых ходов.**

Серверные тесты на 60–120 ходов не заменяют реальную проверку поведения GPT.
