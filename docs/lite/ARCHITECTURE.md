# Архитектура Lite

## Активный код

`models.py` — типизированный технический контракт. `store.py` — файлы, контекст,
память, отношения, транзакции и аудиты. `server.py` — два тонких интерфейса:
MCP и Actions REST. Ни один не вызывает старый движок или внешний генератор.
Только `engine/rules.md` и `engine/skin_builder.md` обязательны каждый ход.

В данных сессии: original.md, novel.md, relationships.md, state.md, timeline.md,
history.jsonl, system/meta.json. knowledge/NPC_ID.md создаётся по необходимости.
JSON-блоки в Markdown используются для отношений, состояния и приобретённых
знаний: читаемая точная структура, один файл каждого назначения. Биографий,
карточек, отдельных файлов сцен/аудитов и повторного резюме канона нет.

## Запись и восстановление

Linux directory flock сериализует все операции сессии без отдельного lock-файла.
Все обращения идут через API: прямое чтение файлов во время транзакции не
обеспечивает согласованный снимок. Данные принадлежат одному экземпляру
файлового хранилища с локальной POSIX-файловой системой, не NFS/object storage.

До записи файлов meta.json атомарно получает pending: полный after-image и
следующие метаданные. Он fsync-ится первым. Затем меняются затронутые файлы,
последним — committed meta.json. При аварии следующий API-вызов под блокировкой
доигрывает pending до целого состояния. При пойманном исключении старые образы
восстанавливаются. Окончательная неустранимая ошибка устройства требует
восстановления диска/резервной копии, её нельзя исправить обещанием atomic.
Читатель повторяет request_id и узнаёт, завершилось ли сохранение.

meta.json также хранит версию, контрольные суммы, ID, подтверждения, bounded
контекстные пакеты/квитанции, ключи идемпотентности, before-image последнего хода
и архив служебных операций. Это технические данные существующего файла, а не
новая многослойная runtime-структура.

history.jsonl логически append-only: полные turn-записи и rollback-записи.
Для простоты безопасной замены физически файл переписывается транзакцией.
Поэтому запись линейна по размеру истории; для очень больших романов нужно
измерение нагрузки, а не заявление о бесконечной масштабируемости. История
не сокращается. Отменённые сцены остаются в архиве; обычный поиск возвращает
действующую ветку истории.

## Границы гарантий

Сервер проверяет целостность, версии, типы/ID, диапазоны и причины изменений,
чтение чанков, источники и цитаты, область аудита, неизменяемость канона.
Он НЕ доказывает, что GPT прочитал/понял файл, что фраза соответствует характеру,
что цитата логически подтверждает знание, или что выдуманная причина объективна.
Эти проверки выполняются GPT и подтверждаются настоящей игровой приёмкой.
Отдельный литературный оценщик намеренно отсутствует.

Подтверждение читателя передаёт клиент: API проверяет наличие и хеш, но не может
сам установить, действительно ли человек его дал. Персональный доступ к серверу
защищается отдельным Bearer-токеном; сессии изолированы по данным, не являются
разными аккаунтами. Мультипользовательский ACL в эту тестовую версию не входит.

Реестр ID фиксируется при создании. Уже зарегистрированный NPC может войти
в любой момент через новый контекст. Совершенно новый постоянный NPC
добавляется через явно согласованную поправку полного канона с registry_additions;
старые ID менять нельзя. Автоматическая миграция старых CN_ сессий не реализована. Новые большие исходники клиент собирает из частей до create;
побайтового потокового загрузчика в этой версии нет. Текст UTF-8, включая CRLF,
сохраняется дословно. Все стадии approval/setup/turn/audit используют версии.
