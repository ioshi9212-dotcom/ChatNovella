# ChatNovella V2 — самостоятельный новый движок

**Изолированная версия.** Вся новая механика находится в папке
novella_v2/. Старые chatnovella/, chatnovella_lite/, старые плагины,
текущий amvera.yaml и данные /data не изменяются. Никаких автоматических
миграций и переключений рабочих сессий.

Это **первая исполняемая версия ядра**, а не автоматически развёрнутый
production-сервер и не полностью настроенная ChatGPT-интеграция. Подключать
её к Amvera и удалять старые файлы стоит только после приёмочных испытаний.

## Принципы

- После «Начнём» модель распределяет **исходные дословные фрагменты** по
  novel.md и characters/<english_name>.md. Сервер принимает только точные
  диапазоны [start,end) в original.txt, проверяет, что ни один символ
  не пропал и ничего не дублируется. Модель обязана выбрать диапазоны;
  сервер не пытается угадать художественную структуру.
- Каждый файл персонажа = короткое правило + авторский текст 1:1.
  Список имён только в novel.md; отдельного игрового cast.json нет.
- Жанровые уточнения оформляются отдельным блоком novel.md после
  утверждения читателем, не изменяя исходный текст.
- Память knowledge/<name>.md — только новые факты, полученные именно
  этим персонажем. Источник цитируется из готовой сцены; из одних
  совпадений слов нельзя автоматически доказать реальное узнавание.
- timeline.md — короткие вехи; ни категории значимости, ни отчёта «почему
  не произошло события» не требуется.
- state.md — строгая физика текущей сцены, без знаний и биографий.
- relationships.md — один JSON-документ: индивидуальные числа NPC→POV
  и направленные описания NPC→NPC. JSON здесь служебный, не анкета.
- В архиве history.jsonl полная художественная сцена и исходное
  сообщение игрока; обычный запрос истории читает только действующие
  ходы, откат не стирает архивный источник.
- Аудиты на 15-м и 60-м ходах обязательны и блокируют следующий ход,
  пока не завершены. Исправления аудита документируются целиком
  в system/audit.jsonl; не меняют original.txt или history.jsonl.

## Что в папке

- engine.py — ядро хранения, проверки, подготовка пакета, чанки 36000
  символов Unicode, SHA-256 и квитанции чтения, атомарное сохранение,
  идемпотентность, откат, аудит, поиск по истории.
- api.py — отдельный HTTP API на FastAPI; все операции, кроме /healthz,
  закрыты Bearer-токеном. Отсутствие токена запрещает доступ.
- rules.md — только механика V2.
- skin_builder.md — **точная копия** прежнего engine/skin_builder.md
  (не менялся; в отдельной папке останется после очистки репозитория).
- tests/test_engine.py — проверки ядра.

## Разработка и локальные тесты

Из корня репозитория:

    python -m unittest discover -s novella_v2/tests -v

Для API:

    pip install -r novella_v2/requirements.txt
    export CHATNOVELLA_V2_DATA_DIR="$(pwd)/.novella_v2_data"
    export CHATNOVELLA_V2_TOKEN="установите_длинную_случайную_строку_минимум_24_символа"
    uvicorn novella_v2.api:app --host 127.0.0.1 --port 8000

Для будущего развёртывания назначить **отдельный** каталог данных,
например /data/chatnovella-v2, не /data/chatnovella-lite. НЕ переключать
текущий Amvera-сервис на новый модуль без проверки.

## Основные API действия

Все пути, кроме healthz, начинаются с /v2/novels.

- POST /v2/novels — original, blocks, names, необязательные genre_answers
  и relationships. Возвращает session_id и canon_hash.
- POST /{sid}/approve — expected_version, canon_hash, confirmation.
- POST /{sid}/opening — expected_version, state, необязательные relationships.
- POST /{sid}/characters — добавить реально появившегося персонажа.
- POST /{sid}/prepare — reader_text, participants, kind=turn|audit.
- GET /{sid}/chunks/{packet_id}/{index} — получить часть и отметку чтения.
- POST /{sid}/turns — атомарно сохранить ход.
- POST /{sid}/rollback — откатить ровно последний ход.
- POST /{sid}/audit — завершить обязательный аудит с отчётом/исправлениями.
- GET /{sid}/history — поиск по полным сохранённым сценам.
- GET /{sid} — статус и актуальная версия.

В prepare возвращаются chunk_count, chunk_hashes и общий SHA-256.
**Прочитать ВСЕ чанки перед сохранением**, сохраняя packet_id и версию.
Чанки содержат не более 36000 символов (не байт). После каждого
нового prepare старый пакет недействителен.

### Дословное распределение исходного текста

Отрезки задаются номерами символов Python/Unicode, **конец не включён**.
Например, оригинал:

    Город.\nАдриан упрямый.\n

Модель должна отправить:

    original: "Город.\nАдриан упрямый.\n"
    names: {"adrian":"Адриан"}
    blocks:
      - {start: 0, end: 7, target: "novel"}
      - {start: 7, end: 23, target: "adrian"}

Это только иллюстрация; фактические индексы нужно посчитать по полученному
оригиналу, а не перепечатывать числа из примера. Непокрытый символ или
пересечение вызывает SOURCE_COVERAGE. Один герой может иметь несколько
несмежных исходных блоков, которые попадут в файл в исходном порядке.

### Состояние

Перед первой сценой задайте opening.state с turn=0:

    {
      "turn":0, "datetime":null, "location":"Гостиная",
      "pov":{"position":"у двери","clothing":"платье",
             "footwear":"туфли","items":[],"physical":"",
             "unfinished":[]},
      "present":{}, "remote":{}, "objects":[], "unfinished":[]
    }

Для нового хода укажите все восемь полей и turn=предыдущий+1.
В present ключи — английские имена участников, значения — такие же
физические Actor-поля, как у pov. В remote — способ связи, а не знания.

### Сохранение хода

Передать request_id, expected_version, packet_id, chunk_hashes,
reader_text, narration, participants, state, knowledge, events, relations.

- knowledge: [] или [{owner:"adrian", fact:"...", source:"точная цитата из narration"}].
  Факт пишется в knowledge/adrian.md и не распространяется другим героям.
- events: [] или [{text:"Краткая веха", participants:["pov","adrian"]}].
- relations: [] или [{source:"adrian",target:"pov",metric:"доверие",
  value:53,reason:"..."}]. Для NPC→NPC metric=null, value — строка.

Повторить тот же request_id с **точно тем же содержимым** после
тайм-аута — безопасно. Изменить payload при повторе нельзя.

### Аудит и откат

При audit_due=15 либо 60 подготовить kind=audit, прочитать чанки и
передать отчёт по continuity, state, knowledge, timeline, relationships.
Для 60-го добавить long_term. Обязательные поля отчёта существуют
только в запросе аудита, не в игровой хронологии.

corrections необязателен. Его запись содержит before_sha256, after
(полный исправленный текст) и reason. Можно исправить state.md,
relationships.md, timeline.md и отдельные knowledge/*.md; оригинал
и историю сцены — нельзя. Изменение фиксируется в audit.jsonl
с полной версией до и после, чтобы исправление было проверяемым.

rollback принимает expected_version, request_id последнего хода и
причину. После завершённого аудита откат предыдущего хода недоступен;
история сохраняется. При сбое записи pending-журнал позволяет
завершить транзакцию при следующем обращении к сессии.

## Чего пока нет

- Автоматического извлечения/классификации блоков средствами LLM внутри
  сервера: это действие ChatGPT при создании новеллы через API.
- Настроенного подключения ChatGPT/MCP и развёрнутого Amvera V2.
- Миграции старых сессий Lite.
- Доказательства **семантической** правильности личных знаний одним кодом.
  Источник проверяется буквально, смысл и доступность POV/NPC —
  моделью и аудитом.
- Приёмочного прогона настоящей длинной новеллы в ChatGPT.

Не удаляйте рабочие файлы старой версии и не переключайте сервер
до отдельной приёмки и резервной копии данных.
