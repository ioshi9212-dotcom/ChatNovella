# ChatNovella V2 — самостоятельный новый движок

**Единственный действующий движок после переключения main на Amvera:** V2.
Новая механика находится только в novella_v2/. Старые каталоги
chatnovella/, chatnovella_lite/ и прежние плагины в GitHub остаются
нетронутыми, но корневой amvera.yaml запускает **только V2**.
Сохранённые старые LITE_ сессии остаются на диске /data/chatnovella-lite,
но не открываются через V2. Автоматической миграции нет.

Это самостоятельный исполняемый V2-движок. Коммит в main готовит
сборку действующего проекта Amvera; фактический онлайн-статус и
подключение плагина нужно проверять по живому серверу.
Старые файлы не удалять и не мигрировать автоматически.

## Принципы

- После «Начнём» модель распределяет **исходные дословные фрагменты** по
  novel.md и characters/<english_name>.md. Сервер принимает только точные
  диапазоны [start,end) **или короткие уникальные дословные anchor-фразы**
  в original.txt, проверяет, что ни один символ не пропал и ничего не
  дублируется. Модель назначает файлы; сервер не угадывает художественную структуру.
- Каждый файл персонажа = короткое правило + авторский текст 1:1.
  Список имён только в novel.md; отдельного игрового cast.json нет.
- Жанровые уточнения оформляются отдельным блоком novel.md после
  утверждения читателем, не изменяя исходный текст.
- Память knowledge/<name>.md — только новые факты, полученные именно
  этим персонажем. Источник цитируется из готовой сцены; из одних
  совпадений слов нельзя автоматически доказать реальное узнавание.
- timeline.md — короткие вехи; ни категории значимости, ни отчёта «почему
  не произошло события» не требуется.
- state.md — строгая физика текущей сцены, без знаний и биографий.
- relationships.md — один компактный JSON-документ с коротким правилом,
  **разреженным направленным знакомством** (нет записи = не знает),
  индивидуальными числами NPC→POV и краткими словесными связями
  NPC→NPC. Перемены заменяют записи, а не дописывают журнал.
- open_threads.md — короткий список незавершённых арок, вопросов и
  договорённостей, загружается **каждый ход**, а не один раз на чат.
  Закрытые линии остаются в архиве, но исчезают из рабочего файла.
- В архиве history.jsonl полная художественная сцена и исходное
  сообщение игрока; обычный запрос истории читает только действующие
  ходы, откат не стирает архивный источник.
- Аудиты на 15-м и 60-м ходах обязательны и блокируют следующий ход,
  пока не завершены. Исправления аудита документируются целиком
  в system/audit.jsonl; не меняют original.txt или history.jsonl.

## Что в папке

- engine.py — ядро хранения, проверки, подготовка пакета, чанки 36000
  символов Unicode, SHA-256 и квитанции чтения, атомарное сохранение,
  идемпотентность, откат, аудит, поиск по истории.
- api.py — отдельный HTTP API на FastAPI и V2 MCP по /mcp,
  без обязательного токена. Публичный адрес открывает API всем;
  любой с ID сессии сможет читать и изменять её содержимое.
- mcp_adapter.py, mcp_models.py — 13 типизированных V2-инструментов,
  не импортирующих Lite; MCP_INSTRUCTIONS.md задаёт порядок их применения.
- build_plugin.py — сборка отдельного приватного плагина после проверки
  фактического публичного V2 URL; паролей в архиве нет.
- rules.md — готовые технические правила V2, включая загрузку один раз
  на чат и обновление по команде.
- templates/relationships.md — короткое начальное правило, которое
  помещается прямо внутрь файла отношений каждой новой сессии.
- relations.py — проверка направленных знакомств, шкал и значимых
  изменений без художественного анализа и без планировщиков.
- threads.py — компактные незавершённые арки с цитатами-основаниями,
  устойчивым id и короткими статусами; никаких сюжетных таймеров.
- skin_builder.md — авторский художественный файл текущей ветки;
  адаптер передаёт его полностью и дословно, включая исходные переводы строк.
  Никакого наследования старой версии или автоматического переписывания.
- tests/ — все регрессионные проверки ядра и HTTP API.

## Разработка и локальные тесты

Из корня репозитория:

    python -m unittest discover -s novella_v2/tests -v

Для API:

    pip install -r novella_v2/requirements.txt
    export CHATNOVELLA_V2_DATA_DIR="$(pwd)/.novella_v2_data"
    uvicorn novella_v2.api:app --host 127.0.0.1 --port 8000

Для работающего сервиса main каталог V2: **/data/chatnovella-v2**,
отдельно от сохранённых Lite-сессий в /data/chatnovella-lite.
Назад к Lite можно вернуться через прежний коммит amvera.yaml;
данные на /data не удалять.

## Основные API действия

Игровые действия начинаются с /v2/novels, а инструкции читаются отдельно
через /v2/instructions. V2 не требует авторизации. Если Amvera
открывает этот URL всем, API будет публичным; не передавайте туда
чувствительные данные без ограничения доступа средствами хостинга.

- GET /v2/instructions — **полный текст Rules и Skin Builder**, их SHA-256,
  длины, признак пустого Skin Builder; только при начале чата и обновлении.
- GET /v2/instructions/versions — **только контрольные суммы**, без текстов;
  необязательная проверка перед ручным обновлением.
- POST /v2/novels — original, blocks, names, необязательные genre_answers,
  relationships и initial_threads. Возвращает session_id и canon_hash.
  У каждого initial_thread поля id/title/status/note/source; source —
  дословная цитата из original.
- POST /{sid}/approve — expected_version, canon_hash, confirmation.
- POST /{sid}/opening — expected_version, state, необязательные relationships.
- POST /{sid}/characters — проверить временное предложение NPC (без записи).
  Передать proposal в prepare.new_characters; только проверенный commit
  регистрирует реально появившегося NPC, а rollback удаляет созданные файлы.
- POST /{sid}/prepare — reader_text, participants, kind=turn|audit|canon,
  необязательный постоянный request_id для игрового хода.
- GET /{sid}/chunks/{packet_id}/{index} — получить часть и отметку чтения.
- POST /{sid}/turns — атомарно сохранить ход.
- POST /{sid}/rollback — откатить ровно последний ход.
- POST /{sid}/audit — завершить обязательный аудит с отчётом/исправлениями.
- GET /{sid}/history — поиск по полным сохранённым сценам.
- GET /{sid} — статус и актуальная версия.

В prepare возвращаются chunk_count, chunk_hashes и общий SHA-256.
**Прочитать ВСЕ чанки перед сохранением**, сохраняя packet_id и версию.
Чанки содержат не более 36000 символов (не байт). После каждого
**действительно нового** prepare старый пакет недействителен.
Повтор при тех же данных и request_id возвращает **прежний пакет**
(reused_pending_packet=true) и прогресс чтения: unread_chunk_indices,
next_chunk_index, all_chunks_read. Не запрашивайте прочитанные чанки
заново, они уже подтверждены сервером. Чанки теперь читаются напрямую
по диапазону байтов из сохранённого пакета без повторного разбора всего файла.

Для нового хода рекомендуется заранее назначить request_id. Если этот ID
уже был успешно сохранён, prepare вернёт already_committed_duplicate=true,
полную оригинальную narration и номер хода **без нового пакета**.
Верните прежнюю сцену, не генерируйте новую. Одинаковый текст игрока
с новым request_id — обычный новый игровой ход, не дубликат.

Технические повторы после timeout/5xx — тот же request_id и та же
операция, **не более двух повторов**. Ошибку валидации исправлять по
её code, а не запускать prepare бесконечным циклом.

## Rules → последние сцены → игровой контекст → Skin Builder

При начале чата GET /v2/instructions?rules_only=true (или MCP
load_v2_instructions(rules_only=true)) возвращает только Rules. Полная пара
остаётся доступной для явного просмотра. На каждом новом ходе prepare
читает актуальные файлы из запущенной версии V2 и формирует упорядоченный
JSON: rules, recent_scenes (до трёх полных активных ходов, по возрастанию),
затем все игровые сведения. Skin Builder передаётся последним, отдельным
блоком из одного или нескольких чанков. skin_chunk_start указывает первый
его чанк. Ничего игрового после текста Skin Builder нет. Проверки получают
разделы и ID строк из этого же блока. Чтение по next_chunk_index обязательно.
При неизменных исходных файлах повтор запроса сохраняет старый packet_id;
при изменении Rules/Skin Builder создаётся новый пакет. Старый пакет не
может быть сохранён. Audit и canon содержат Rules, но не Skin Builder.
Аудит по-прежнему получает 15 последних полных сцен. Пустой авторский
файл не заменяется старым. GitHub не гарантирует развёртывание на Amvera.


## relationships.md — один источник текущих отношений

В каждом игровом пакете присутствует **один** relationships.md
со встроенным коротким правилом. В нём четыре раздела:

- rules — краткая инструкция: отношения влияют на поступки, но
  не заменяют характер, не дают чужих знаний и не переименовывают
  установленные автором чувства.
- familiarity — **разреженная** направленная карта знакомства
  **включая POV**: отсутствие пары означает unaware (не знает),
  aware — знает заочно, acquainted — знаком лично. Направления
  независимы. Ненужной таблицы всех незнакомых пар нет.
- npc_to_pov — произвольные авторские названия шкал 0..100, максимум
  десять на одного персонажа. Для ещё незнакомого NPC шкал нет.
- npc_to_npc — краткое текущее описание словесной связи, максимум
  240 символов на направление. Для незнакомого направления запись
  отсутствует.

При создании можно передать familiarity вместе с начальными
отношениями из анкеты. Неназванные знакомства считаются неизвестными;
уже указанные старые числовые/словесные связи сохраняются без
переименования и подразумевают знакомство при совместимости со старой
схемой. Изменение знакомства и чувств — отдельные элементы relations,
можно передать их одним commit. Отношения меняются только для
участников сцены, включая наблюдение или разговор на расстоянии,
а не за счёт всеведущего контекста.

Если отношений не поменялось, файл вообще **не перезаписывается**.
Причина перемены остаётся в полном history.jsonl, а в рабочем файле —
только текущие значения. Новый персонаж не создаёт строки
«не знаком» для всего состава — связи добавляются по факту.

Содержимое Skin Builder берётся из текущего авторского файла V2.
Художественные формулировки и стиль задаёт автор.

## open_threads.md — всегда с моделью

В каждом пакете turn, audit и canon передаётся один короткий файл
незавершённых линий; он НЕ повторяет художественные инструкции.
Одна строка на линию: стабильный id, «не началась» либо «активна»,
краткий последний факт, ход. При существенном развитии заменить
строку, при доказанном завершении удалить её из рабочего файла.
Исход остаётся в history.jsonl. Не более 48 открытых линий одновременно.

Для нового хода необязательное поле **thread_updates**: список
{id,title,status,note,source}; status=not_started|active|closed,
а source — дословная выдержка из narration.
Отсутствие изменений = [] или отсутствие поля. Нет сюжетных
дедлайнов, расписаний раскрытий и обязательных событий.

## Граница знаний и реальные участники сцены

- Просто включить NPC в prepare и commit недостаточно для передачи
  сведений или изменения отношений: персонаж должен находиться в
  present/remote **в конце сцены** либо иметь документированный
  доступ **внутри** хода. Участие в предыдущем ходе не доказывает
  присутствие после смены времени и места. Для вошедшего и ушедшего за один ход
  передайте необязательный **scene_access**:
  [{character:"silas",channel:"ability",source:"дословная цитата из narration"}].
  Возможные channel: physical, remote, ability. Фальшивые цитаты
  отклоняются. Это не требует оставлять персонажа в конечной комнате.
- Перед публикацией каждой реплики — один короткий проход по тому,
  что говорящий действительно мог знать: карточка, персональные
  приобретённые знания, известное общее прошлое, допустимое
  восприятие. У режиссёра есть полный мир, но NPC не получает его
  секретов автоматически. Это не запрет личных воспоминаний,
  бытовой импровизации, лжи, блефа или догадок.
- Предупреждение **POSSIBLE_UNFAMILIAR_NAME:source:target** отмечает,
  что персонаж произнёс имя другого, о ком не было знакомства в
  текущем файле. Это подсказка для проверки, а не отказ сохранения:
  имя могло прозвучать впервые в этой же сцене. Полной автоматической
  проверки семантики прозаических утверждений не существует.

## Длительная игра и аудит

- Хронология не переписывается при отсутствии новых вех.
- В оперативных системных метаданных хранятся последние **32**
  квитанции ходов; постоянный небольшой фильтр позволяет обрабатывать
  новые ID быстро, а старые повторные вызовы сверяются с полным
  архивом. Повтор старого сохранения не создаёт второй ход.
- Скачок существующего NPC→POV показателя более чем на 3 требует
  significant:true, объяснение reason и **evidence** — точную
  цитату из сохраняемой narration, не только красивую причину.
- При аудите изменение отношений должно иметь цитату из
  original.txt либо сохранённой сцены и не может подменить rules.
  Новые дополнения к knowledge/timeline при аудите тоже требуют
  реальную цитату из сцены; для knowledge цитата должна происходить
  из хода, где участвовал конкретный владелец знания.
- Это техническая проверка сохранности и происхождения записей,
  **не доказательство** того, что модель семантически правильно
  интерпретировала реплику. Отдельная игровая приёмка обязательна.

## Дополнительные небольшие защиты

- **Контекст:** старый packet возвращается без повторной сборки,
  если состав участников, ввод, версия и исходные файлы не изменились.
  Если изменились игровые знания или состояние — подготовится новый
  пакет. Обновление Rules/Skin Builder **не перестраивает** игровой пакет:
  эти файлы больше не являются его частью.
- **Целостность:** оригинал проверяется перед утверждением и на аудитах.
  Контрольные суммы главной анкеты и карточек сверяются при обычной
  подготовке. Перед сохранением проверяются версия и состояние источников
  подготовленного пакета.
- **Архив:** новые записи добавляются в history.jsonl, а не вызывают
  переписывание всей истории. Pending-журнал позволяет безопасно
  завершить даже прерванное посередине добавление. Для последних трёх
  сцен чтение идёт с конца архива, а не с самого начала.
- **Повтор сцен:** если длинная новая сцена почти повторяет недавнюю,
  сервер всё равно сохраняет её, но отдаёт предупреждение
  SCENE_NEAR_DUPLICATE в ответе commit. Принудительных сюжетных поворотов,
  обязательных событий или художественных оценок нет.
- **Без лишних проверок:** аудиты 15/60 остаются обязательными,
  а перед обычным ходом работают только быстрые технические проверки.
  Сервер не превращается в литературного цензора.

### Дословное распределение исходного текста

Для реальной длинной анкеты предпочтительнее **маркеры из точного текста**:

    original: "Мир: город.\nАдриан: упрямый.\n"
    names: {"adrian":"Адриан"}
    blocks:
      - {anchor: "Мир: город.", target: "novel"}
      - {anchor: "Адриан: упрямый.", target: "adrian"}

Каждый маркер должен встречаться в оригинале ровно один раз и начинать
новый фрагмент. Движок сам высчитает смещения, сохраняя текст 1:1.
Если маркер неоднозначен, сервер отклонит разбор, а не угадает.

Альтернативно отрезки задаются номерами символов Python/Unicode,
**конец не включён**. Например, оригинал:

    Город.\nАдриан упрямый.\n

Модель должна отправить:

    original: "Город.\nАдриан упрямый.\n"
    names: {"adrian":"Адриан"}
    blocks:
      - {start: 0, end: 7, target: "novel"}
      - {start: 7, end: 23, target: "adrian"}

Это только иллюстрация; фактические индексы нужно посчитать по полученному
оригиналу, а не перепечатывать числа из примера. Непокрытый символ или
пересечение вызывает SOURCE_COVERAGE. Один герой может иметь несколько
несмежных исходных блоков, которые попадут в файл в исходном порядке.

### Состояние

Перед первой сценой задайте opening.state с turn=0:

    {
      "turn":0, "datetime":null, "location":"Гостиная",
      "pov":{"position":"у двери","clothing":"платье",
             "footwear":"туфли","items":[],"physical":"",
             "unfinished":[]},
      "present":{}, "remote":{}, "objects":[], "unfinished":[]
    }

Для нового хода укажите все восемь полей и turn=предыдущий+1.
В present ключи — английские имена участников, значения — такие же
физические Actor-поля, как у pov. В remote — способ связи, а не знания.

### Сохранение хода

Передать request_id, expected_version, packet_id, chunk_hashes,
reader_text, narration, participants, state, knowledge, events, relations.
Опционально: thread_updates и scene_access.

- knowledge: [] или [{owner:"adrian", fact:"...", source:"точная цитата из narration"}].
  Факт пишется в knowledge/adrian.md и не распространяется другим героям.
- events: [] или [{text:"Краткая веха", participants:["pov","adrian"]}].
- relations: [] либо знакомство
  [{source:"adrian",target:"pov",status:"acquainted",reason:"Первая встреча"}]
  и/или оценка [{source:"adrian",target:"pov",metric:"доверие",
  value:53,reason:"...",significant:false}]. Для NPC→NPC metric=null,
  value — короткая (до 240 символов) словесная связь. При изменении
  существующей шкалы более чем на 3 пункта передать significant:true,
  конкретный reason и evidence — дословный отрывок из сцены.
  Первое значение новой шкалы — исходная оценка,
  а не скачок из нуля. Необязательное significant можно не передавать.

Повторить тот же request_id с **точно тем же содержимым** после
тайм-аута — безопасно. Изменить payload при повторе нельзя.

### Аудит и откат

При audit_due=15 либо 60 подготовить kind=audit, прочитать чанки и
передать отчёт по continuity, state, knowledge, timeline, relationships.
Для 60-го добавить long_term. Обязательные поля отчёта существуют
только в запросе аудита, не в игровой хронологии.

corrections необязателен. Его запись содержит before_sha256, after
(полный исправленный текст) и reason. Можно исправить state.md,
relationships.md, timeline.md и отдельные knowledge/*.md; оригинал
и историю сцены — нельзя. Изменение фиксируется в audit.jsonl
с полной версией до и после, чтобы исправление было проверяемым.

rollback принимает expected_version, request_id последнего хода и
причину. После завершённого аудита откат предыдущего хода недоступен;
история сохраняется. При сбое записи pending-журнал позволяет
завершить транзакцию при следующем обращении к сессии.

## Чего пока нет

- Автоматического извлечения/классификации блоков средствами LLM внутри
  сервера: это действие ChatGPT при создании новеллы через API.
- Настроенного подключения ChatGPT/MCP и развёрнутого Amvera V2.
- Миграции старых сессий Lite.
- Доказательства **семантической** правильности личных знаний одним кодом.
  Источник проверяется буквально, смысл и доступность POV/NPC —
  моделью и аудитом.
- Приёмочного прогона настоящей длинной новеллы в ChatGPT.

Не удаляйте рабочие файлы старой версии и не переключайте сервер
до отдельной приёмки и резервной копии данных.
